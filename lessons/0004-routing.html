Урок 4 · Микрофронтенды

Роутинг: один адрес, много микрофронтендов

Адресная строка у вкладки одна, а роутеров хочется по одному на каждый МФ. После урока вы сможете объяснить, кто владеет URL, как МФ получает «свою» часть адреса и почему переход в обход контракта тихо ломает страницу.

Разминка: урок 3

Почему Shell может рендерить <Catalog /> только при shared: { react: { singleton: true } }, а для Корзины через mount(el) это не нужно? Ответьте, потом откройте.

Компонент Каталога рендерит react-dom Shell, и хуки должны обращаться к той же копии React, иначе useState of null. При mount(el) remote рендерит сам, своей собственной парой React + ReactDOM (или Vue), так что всё согласовано. Цена — две копии фреймворка на странице. Вы как раз проверяли это своим catalog/src/mount.tsx.

Два уровня одного адреса

Так устроен пример в канонической статье. Контейнер сопоставляет URL со списком маршрутов и решает, какой МФ монтировать. А «собственная логика роутинга» МФ потом извлекает из URL ID ресторана и показывает нужное[1]. В «Полке» таблица Shell — это два префикса (shell/src/router.ts), а /book/:sku знает только Каталог.

Три правила

  1. История одна, и меняется через один контракт. В статье контейнер передаёт всем МФ один и тот же объект history, и тогда «изменения маршрута, вызванные в любом из роутеров, отражаются во всех»[1]. У нас то же самое, но без зависимости от библиотеки: Shell передаёт вниз path и функцию navigate(to). React-компоненту — через props, Vue-Корзине — аргументом mount(el, { navigate }).

  2. Переход в обход контракта Shell не увидит. «Просто вызвать history.pushState() или history.replaceState() — popstate не сработает»: он срабатывает только на действия браузера вроде кнопки «Назад»[2]. Если Каталог сам сделает pushState('/cart'), адрес сменится, а страница нет.

  3. Адрес — публичный контракт между командами. Корзина ведёт на /catalog/book/:sku, то есть знает формат адреса чужого МФ. Статья прямо говорит: выбранные маршруты «составляют контракт», их нельзя поменять, не обновив все приложения, которые на них ссылаются, и это нужно проверять автоматическими тестами[1].

Не забудьте про сервер

Пользователь может обновить страницу на /catalog/book/dune или открыть её по ссылке из письма. Сервер должен отдать на этот путь index.html Shell, а дальше разберётся роутер. vite preview делает это сам (я проверил: 200 и страница Shell). В проде это отдельная настройка сервера или CDN.

Лабораторная

Я обновил playground: в Shell появился роутер, у Каталога — страница книги, у Корзины — своя страница /cart на Vue. Внизу Shell есть диагностическая полоска: «адрес / что смонтировано». Если ваши серверы ещё работают, просто обновите страницу. Если нет: cd playground && npm start.

  1. Глубокая ссылка. Откройте localhost:5170/catalog/book/dune напрямую. Кто из двоих понял, что нужно показать «Дюну»? Оба, но по-разному. Shell по префиксу /catalog выбрал МФ, а Каталог по хвосту /book/dune выбрал книгу. Shell про книги ничего не знает.
  2. Туда и обратно. «Перейти в корзину» → в Корзине кликните по книге → дважды «Назад» в браузере. Куда приведёт каждое «Назад»? Сначала на /cart, потом снова на книгу. Переходы шли через navigate(), поэтому в истории три записи, а на «Назад» Shell узнаёт о смене через popstate. React и Vue живут на одной истории.
  3. Поломка. На странице книги нажмите красную кнопку «⚠ В корзину через history.pushState». Что покажут адрес, страница и полоска? Адрес станет /cart, а на странице останется книга. Полоска покраснеет: «рассинхрон: по адресу должен быть cart-page». Обновите страницу (F5), и всё станет правильно. Поэтому такой баг легко пропустить в разработке.
  4. 404. Откройте localhost:5170/nope. Чья это страница ошибки? Shell: путь не совпал ни с одним префиксом таблицы. «Не найдено» на уровне префиксов — ответственность Shell. А «книга не найдена» по /catalog/book/xxx — уже Каталога, попробуйте.

Задача на код: страховочная сетка

Сделайте так, чтобы Shell замечал любую смену адреса, даже в обход navigate(), и шаг 3 перестал ломаться. Подсказка: Navigation API, «преемник History API, нацеленный на нужды SPA»[3]. Нужно событие, которое срабатывает после смены текущей записи истории. Правьте shell/src/router.ts, затем выполните npm run build -w shell и повторите шаг 3.

Решение (проверено на нашем стенде) 
useEffect(() => {
  if (!('navigation' in window)) return          // старые браузеры: сетки нет, живём на контракте
  const sync = () => setPath(location.pathname)
  navigation.addEventListener('currententrychange', sync)
  return () => navigation.removeEventListener('currententrychange', sync)
}, [])

В Chrome я проверил: currententrychange срабатывает на pushState (тип push), replaceState (replace) и «Назад» (traverse), и location к этому моменту уже обновлён. С этим кодом полоска на шаге 3 остаётся зелёной.

Почему это сетка, а не замена контракту: у Navigation API статус «Baseline 2026, newly available», то есть «может не работать в старых устройствах и браузерах»[3]. Контракт navigate() работает везде и делает намерение явным.

Проверьте себя

Последние два вопроса — из уроков 3 и 2.

Кто решает, что означает /book/dune в адресе /catalog/book/dune?

Shell хранит адрес и по префиксу выбирает МФ, но хвост не интерпретирует. Иначе каждая новая страница Каталога требовала бы релиза Shell, и независимая поставка пропала бы.

Каталог вызвал history.pushState(null, '', '/cart') напрямую. Почему Shell не смонтировал Корзину?

popstate срабатывает только на действия браузера: «Назад», «Вперёд», history.back()[2]. Ничего не запрещено и ничего не заблокировано, просто никто не сказал Shell о переходе.

Корзина ссылается на /catalog/book/:sku. Команда Каталога хочет перейти на /catalog/books/:sku. Что здесь главное?

Формат адреса — публичный API команды, как exposes. Обычно его меняют через переходный период: старый адрес поддерживают и редиректят, пока все потребители не обновятся. Тесты на контракт ловят забытых потребителей[1].

Пользователь обновил страницу на /catalog/book/dune и получил 404 от сервера, а не от приложения. В чём причина?

404 от сервера значит, что до JavaScript дело не дошло. Если бы Shell не знал префикс, была бы его собственная страница «не найдено», как на шаге 4. exposes описывает модули, а не адреса.

урок 3 Каталог отдаётся через mount(el) и сам вызывает createRoot своим react-dom. Нужен ли shared singleton?

Каталог рендерит своей парой React + ReactDOM, поэтому хуки согласованы. Это ваш эксперимент с mount.jsx. Singleton здесь — экономия трафика, а не условие работы. Фреймворк Shell роли не играет.

урок 2 На /cart бейдж в шапке и страница корзины — оба из МФ Корзины. Как им лучше делить состояние?

Правило «нет общего состояния» действует между командами. Внутри одного МФ один владелец, и общий модуль — норма: в playground это cart/src/store.ts. Оба exposes одного remote используют один экземпляр этого модуля.

Тренировка для собеседования

60 секунд, вслух:

«Как у вас устроен роутинг между микрофронтендами? Кто владеет URL? Что будет, если микрофронтенд сам поменяет адрес?»

Образец ответа

Адрес один, поэтому роутинг двухуровневый. Shell держит таблицу префиксов (/catalog → Каталог, /cart → Корзина), монтирует нужный МФ и показывает 404 на уровне префиксов. Хвост адреса интерпретирует сам МФ: это его подмаршруты, Shell про них не знает, поэтому новые страницы не требуют релиза Shell. История одна: Shell передаёт микрофронтендам текущий путь и функцию navigate (или общий объект history, как в статье Cam Jackson), и все переходы, в том числе внутри МФ, идут через неё. Если МФ сам вызовет pushState, Shell не узнает: popstate на это не срабатывает, адрес и экран разъедутся. Поэтому контракт обязателен, а как страховку можно слушать currententrychange из Navigation API. Формат адресов — контракт между командами, его покрывают тестами. И сервер должен отдавать Shell на любой путь, чтобы работали глубокие ссылки.

Главный источник к уроку
