Урок 3 · Микрофронтенды

Module Federation: как микрофронтенд попадает на страницу

До сих пор «Полка» жила в одном файле. Теперь это три настоящих приложения с отдельными сборками и серверами: Shell и Каталог на React, Корзина на Vue. После урока вы сможете прочитать конфиг Module Federation, объяснить host, remote, exposes и shared и показать, что ломается без singleton.

Разминка: вспомните урок 2

Назовите по памяти четыре проблемы синхронизации состояния и приём для каждой. Потом кликните по размытому тексту.

1) Компонент выгрузили, и данные пропали → состояние живёт у владельца дольше компонента. 2) Опоздавший подписчик → снимок вместо дельты и рукопожатие state-request. 3) Действие потерялось → подтверждение через preventDefault(). 4) Вкладки разъехались → владелец синхронизирует себя через BroadcastChannel.

Какую задачу решает Module Federation

Каноническая статья называет основным способом сборки микрофронтендов runtime-интеграцию через JavaScript: каждый МФ — отдельный бандл со своим адресом, а контейнер подгружает его во время работы страницы[1]. Сделать это вручную можно, но быстро появляются вопросы. Как хосту узнать, какие модули есть у remote? Как не скачать React трижды? Как договориться о версиях?

Module Federation отвечает на них стандартным способом: это «архитектурный паттерн децентрализации JavaScript-приложений», который позволяет приложениям делиться кодом и зависимостями[2]. Сейчас актуальна версия 2.0 с отдельным рантаймом и манифестом. Она работает с webpack и Rspack, а с Vite — через официальный плагин @module-federation/vite[3], который мы и используем.

Пять слов, на которых всё держится

ТерминЧто этоВ «Полке»
hostПриложение, которое потребляет чужие модули во время работыShell, порт 5170
remoteПриложение, которое отдаёт свои модули наружуКаталог (5171), Корзина (5172)
exposesПубличный контракт remote: какие модули под какими именами доступны снаружи. Всё остальное — внутреннее./Catalog, ./mount
remoteEntry.js«Витрина» remote: маленький файл, по которому хост узнаёт про его exposes и shared. Рядом лежит mf-manifest.json с тем же описанием в JSONlocalhost:5171/remoteEntry.js
sharedЗависимости, которые приложения договариваются загрузить один раз и использовать вместеreact, react-dom

Что происходит в браузере

Конфиг: две стороны одного контракта

catalog/vite.config.ts · remote

federation({
  name: 'catalog',
  filename: 'remoteEntry.js',
  exposes: {
    './Catalog': './src/Catalog.tsx',
  },
  shared: {
    react: { singleton: true },
    'react-dom': { singleton: true },
  },
})

shell/vite.config.ts · host

federation({
  name: 'shell',
  remotes: {
    catalog: {
      type: 'module', name: 'catalog',
      entry: 'http://localhost:5171/remoteEntry.js',
    },
  },
  shared: {
    react: { singleton: true },
    'react-dom': { singleton: true },
  },
})

После этого в Shell работает обычный, на вид, импорт: lazy(() => import('catalog/Catalog')). Но он идёт не в node_modules, а по сети на 5171 и в момент вызова. Поэтому Каталог можно передеплоить, не пересобирая Shell. Тип module нужен для ESM-remote на Vite[3].

Два способа встроить remote

Компонент (Каталог)Функция mount(el) (Корзина)
Что отдаёт remoteReact-компонентmount(el) → unmount
Канал «вниз»props: <Catalog user={user} />аргументы mount или атрибуты узла
ТребованиеТот же фреймворк и один экземпляр React (singleton)Ничего: хост даёт DOM-узел, а remote внутри может быть на любом фреймворке
ЦенаКоманды связаны версией фреймворкаКаждый remote везёт свой рантайм (Vue здесь едет внутри Корзины)
Почему singleton — не оптимизация, а требование

Без shared Каталог приносит свою копию React. Shell рендерит его компонент своим react-dom, а хуки Каталога обращаются к другой копии React, где рендер не идёт. Результат я получил на нашем стенде: Cannot read properties of null (reading 'useState'). Документация React называет «больше одной копии React» одной из трёх причин ошибки invalid hook call[4]. При singleton и разных версиях загружается более высокая, а сторона с низкой версией получает предупреждение[5].

Лабораторная: playground

Всё ниже я прогнал в реальном браузере, включая поломки. В терминале:

cd playground
npm install
npm start        # собрать всё и поднять 3 сервера → http://localhost:5170

Перед каждым шагом сделайте ставку. Размытый текст — ответ.

  1. Посмотрите на Network. Откройте DevTools → Network, обновите страницу и найдите remoteEntry.js с портов 5171 и 5172. Загрузится ли React с порта 5171? Нет. Метка Каталога показывает «общий с Shell ✓», а файлов react с 5171 в списке нет. Это singleton в действии.
  2. Независимый деплой. В catalog/src/Catalog.tsx переименуйте «Дюна» в «Дюна (новое издание)», затем: 
    npm run build -w catalog
    Обновите Shell. Нужно ли пересобирать Shell? Нет. Shell знает только адрес remoteEntry.js, а свежий remoteEntry ссылается на новые чанки. Одна оговорка для прода: сам remoteEntry.js нельзя надолго кэшировать, ведь его имя не меняется между деплоями.
  3. Каталог лежит. Остановите всё (Ctrl+C) и запустите без Каталога: 
    npm run preview:no-catalog
    Что будет со страницей и с Корзиной? Вместо Каталога появится заглушка «временно недоступен» от RemoteBoundary (error boundary в Shell). Корзина работает. В консоли будет RUNTIME-008: Failed to load script resources, и в ней ссылка на документацию.
  4. Сломайте singleton. Верните Каталог (npm run preview), удалите блок shared из catalog/vite.config.ts, выполните npm run build -w catalog и обновите страницу. Что сломается и где? Каталог упадёт с Cannot read properties of null (reading 'useState'): у него теперь своя копия React. Error boundary покажет заглушку, остальная страница жива. Верните shared и пересоберите Каталог.

Ещё одна находка с этого стенда. Сначала Корзина отправляла в BroadcastChannel items.value и падала с DataCloneError: Vue хранит данные в реактивных Proxy, и structured clone их не переносит. Мораль для собеседования: через границу МФ передаются простые данные, а не внутренние объекты фреймворка. Решение в CartBadge.vue.

Проверьте себя

Последние два вопроса — из уроков 2 и 1.

Какой файл хост загружает у remote, чтобы узнать, какие модули тот предоставляет?

remoteEntry.js — это «витрина» remote: какие модули есть в exposes и что нужно из shared. Репозиторий Каталога хосту недоступен и не нужен: связь идёт только через задеплоенные файлы.

Команда Каталога исправила текст и задеплоила только Каталог. Что нужно сделать команде Shell?

В этом весь смысл runtime-интеграции: Shell знает адрес, а не версию. Если бы Каталог подключался npm-пакетом (build-time интеграция), понадобились бы шаги b и c. Именно поэтому статья не советует такой вариант: релизы становятся синхронными[1].

Shell и Каталог на React, но shared не настроен. Что произойдёт, когда Shell отрендерит <Catalog />?

Ответ «бандл немного больше» был бы верен для способа mount(el), где каждый рендерит своим React. Но когда компонент рендерит чужой react-dom, две копии React ломают хуки. Мы это видели в шаге 4.

Почему Корзина отдаёт наружу mount(el), а не Vue-компонент?

Отдать Vue-компонент можно, в README плагина именно такой пример[3], но рендерить его сможет только хост на Vue. mount(el) — контракт, не зависящий от фреймворка: «вот DOM-узел, рисуй как хочешь».

урок 2 Корзина на Vue отправляет items.value в BroadcastChannel и получает DataCloneError. Почему?

Массивы и объекты канал передаёт без проблем, если это простые данные. Реактивная обёртка Vue (и вложенные в неё объекты) — Proxy, а его structured clone перенести не может. Разные порты дали бы другой origin, но не эту ошибку: сообщение просто никто бы не получил.

урок 1 Сервер Каталога не отвечает, remoteEntry.js не загрузился. Что должен сделать Shell?

Это та же устойчивость, что в уроке 1, только на уровне загрузки кода. В React её даёт error boundary вокруг Suspense, а для mount — .catch() у import(). Оба варианта есть в shell/src/App.tsx.

Тренировка для собеседования

60 секунд, вслух:

«Что такое Module Federation, чем она лучше подключения микрофронтенда npm-пакетом и зачем нужен shared singleton?»

Образец ответа

Module Federation — это runtime-интеграция: каждый микрофронтенд собирается и деплоится отдельно, публикует remoteEntry.js со списком того, что отдаёт наружу (exposes), а хост по import('catalog/Catalog') загружает этот код по сети во время работы страницы. В отличие от npm-пакета, хосту не нужно пересобираться при каждом релизе remote: он знает адрес, а не версию. shared позволяет загрузить общие зависимости один раз. Для React это требование, а не оптимизация: если хост рендерит компонент remote, а у того своя копия React, хуки падают. Поэтому singleton: true, а при расхождении версий берётся старшая, и рантайм предупреждает. Когда фреймворки разные, remote лучше отдавать функцию mount(el), а не компонент. Обязательно оборачиваем remote в error boundary, чтобы падение одного не роняло страницу.
