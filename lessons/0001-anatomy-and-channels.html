Урок 1 · Микрофронтенды

Анатомия микрофронтендов и три канала связи

После урока вы сможете, глядя на любое действие в интерфейсе, сказать, каким каналом один микрофронтенд должен сообщить о нём другому, и объяснить это на собеседовании за минуту.

Что это вообще такое

Микрофронтенды — это «архитектурный стиль, при котором независимо поставляемые фронтенд-приложения собираются в единое целое»[1]. Ключевое слово здесь независимо поставляемые: каждая команда собирает, тестирует и деплоит свой кусок сама, не дожидаясь остальных. Всё остальное, включая разные фреймворки, — следствие, а не цель.

Поэтому приложение режут по бизнес-доменам (каталог, корзина, аккаунт), а не по техническим слоям («компоненты», «API», «стили»). Одна команда владеет доменом целиком.

Весь курс мы будем разбирать на одном примере: книжный маркетплейс «Полка».

Три канала связи

Главный совет канонической статьи — «чтобы микрофронтенды общались как можно меньше»[1]. Когда общаться всё же нужно, хватает трёх каналов:

↓ Атрибуты / props

Контейнер передаёт данные вниз: «вот текущий пользователь». Явный входной контракт.

↑ События

МФ сообщает о факте: «добавили книгу». Он не знает и не должен знать, кто слушает.

⇄ URL

Намерение пользователя: «открыть каталог фантастики». Переживает перезагрузку, им можно поделиться.

// ↓ Shell → МФ. В React/Vue это были бы props смонтированного компонента.
catalog.setAttribute('user', 'Анна')

// ↑ МФ сообщает факт. Префикс команды в имени, bubbles+composed — чтобы выйти из Shadow DOM.
this.dispatchEvent(new CustomEvent('catalog:add-to-cart', {
  detail: { sku: 'dune', price: 790 }, bubbles: true, composed: true,
}))
// …а Корзина (другая команда, другой бандл) просто слушает:
window.addEventListener('catalog:add-to-cart', (e) => addItem(e.detail))

// ⇄ URL: обычная ссылка. Shell-роутер превратит её в атрибут genre="sf".
<a href="/catalog?genre=sf">Ещё фантастики</a>

Почему нативные события, а не своя шина? Принцип micro-frontends.org: «используйте события браузера для коммуникации вместо собственной глобальной PubSub-системы»[2]. API события есть в любом фреймворке, поэтому стек каждой команды остаётся её личным делом.

Правило состояния

У каждого куска данных ровно один владелец. Корзиной владеет Корзина, входом пользователя — Shell. Остальные получают копии через каналы выше, но никогда не пишут в чужое. Отсюда совет «избегать любого общего состояния»[1] и «не делить рантайм, даже если у всех команд один фреймворк»[2].

Потрогайте руками

Ниже — живая «Полка»: четыре независимых компонента, каждый со своим Shadow DOM и своим состоянием. Журнал под ней ничего не знает о коде приложения. Он подслушивает настоящие каналы: события на window, изменения атрибутов и адресной строки.

Эксперимент: четыре шага, следите за журналом

  1. Нажмите «Войти как Анна». В журнале появится атрибут ↓ от Shell к Каталогу: авторизацией владеет Shell и раздаёт её вниз.
  2. Добавьте в корзину две книги. На каждый клик будет два события: Каталог сообщил факт (catalog:add-to-cart), Корзина обновила своё состояние и сообщила своё (cart:changed). Каталог при этом ничего не знает о Корзине.
  3. Откройте Аккаунт и нажмите «Ещё фантастики». Цепочка: URL ⇄ → Shell смонтировал Каталог → жанр пришёл атрибутом. Аккаунт не знает, кто отрисует каталог, он просто сменил адрес.
  4. Нажмите «Уронить МФ корзины» и добавьте книгу. Каталог продолжает работать, событие просто никто не обрабатывает. Теперь верните корзину и посмотрите на счётчик.

Проверьте себя

Отвечайте по памяти, не прокручивая вверх. Усилие при вспоминании и есть то, что закрепляет знание.

Пользователь нажал «В корзину» в Каталоге. Как правильно обновить счётчик в шапке?

Каталог сообщает факт catalog:add-to-cart, а Корзина, владелец данных, сама решает, что с ним делать. Прямой вызов связывает команды контрактом на внутренний API, общий store нарушает правило одного владельца.

Кто должен владеть информацией о том, вошёл ли пользователь?

Авторизация сквозная, поэтому её обычно держит контейнер и передаёт токен или пользователя каждому МФ[1]. Свои копии у каждого МФ быстро разъедутся: один решит, что вы вошли, другой — что нет.

Аккаунт хочет открыть Каталог сразу с фильтром «фантастика». Какой канал лучше?

Это намерение пользователя, а не факт для подписчиков. URL переживает перезагрузку, им можно поделиться, и Аккаунту не нужно знать, смонтирован ли Каталог. Ставить атрибуты чужим МФ — работа Shell, а не соседа.

МФ Корзины не загрузился. Что происходит с Каталогом в хорошо спроектированной системе?

Событие — это «выстрелил и забыл»: отправитель не зависит от наличия слушателей. Поэтому сбой одной команды не роняет остальных. Это аргумент в пользу событий перед прямыми вызовами.

Зачем называть события с префиксом команды, например cart:changed?

Принцип «префиксов команд»: неймспейсить CSS, события, localStorage и cookies, чтобы избежать коллизий и сделать владение очевидным[2]. Браузеру префикс безразличен, это соглашение между людьми.

Тренировка для собеседования

Засеките 60 секунд и ответьте вслух, прежде чем раскрыть образец:

«Как у вас микрофронтенды общаются между собой и где живёт состояние?»

Образец ответа

Стараемся, чтобы они общались как можно меньше: если два МФ постоянно переговариваются, граница между ними, скорее всего, проведена неудачно. Каналов три. Вниз контейнер передаёт данные через props или атрибуты, например текущего пользователя. Вверх МФ отправляют браузерные события о фактах с префиксом команды, например catalog:add-to-cart, и не знают, кто их слушает. Намерения пользователя передаются через URL. Общего store нет: у каждого куска данных один владелец, корзиной владеет МФ корзины, остальные только получают события. Поэтому падение одного МФ не роняет остальные.
