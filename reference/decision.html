Нужны ли микрофронтенды

МФ решают проблему масштабирования команд. Границы в коде нужны всегда, отдельный деплой — только когда за ним стоят разные команды с разным ритмом.

Сигналы

За микрофронтендыПротив
Много команд на одном UI, боль именно в совместном релизеОдна или несколько команд, общий релиз никому не мешает
Стабильные вертикальные домены, у команд свои бэкенды / BFFДомены ещё ищутся (стартап, прототип) — Monolith First
Каждой команде нужен свой ритм релизов и откатаЧасти постоянно делят состояние (редактор, сложная форма)
Постепенная миграция с легаси (стратегия перехода)Жёсткий бюджет производительности
Есть команда платформы для Shell, CI, мониторингаМотив «каждый пишет на любимом фреймворке» (Radar: anarchy → Hold)

Варианты

АрхитектураКогда
Простой монолитМало людей, границы неизвестны, главное — скорость изменений
Модульный монолитБоль в связанности кода, а не в релизе. Строгие границы, контракты, один деплой
МикрофронтендыБоль в совместном релизе при стабильных вертикальных доменах
МФ как стратегия переходаЛегаси + новый стек: новое рядом со старым, Shell переключает маршруты

Цена на нашем стенде (тот же код)

ЗапросовПередано
Module Federation, 3 сервера38208,7 КБ
Модульный монолит, 1 сборка899,6 КБ

Плюс операционная цена: shared и версии, доступность remote, рассинхрон роутинга, утечки CSS, ошибки между фреймворками, ручные контракты.

Порядок решения

  1. Где боль: в коде (связанность) или в поставке (общий релиз)?
  2. Код → модульный монолит: границы, владельцы, контракты, запрет импортов через границы.
  3. Поставка → вертикальны ли и стабильны ли домены? Нет → сначала найти границы в монолите.
  4. Да → вынести один самый независимый домен в remote, проверить Shell, контракты, деплой и мониторинг.
  5. Сразу договориться о стандартах: основной фреймворк, токены стилей, события, маршруты.
